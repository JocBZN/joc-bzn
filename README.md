# JOC-BZN-Mobile 🎮

A **survivors-like** (bullet-heaven) game — think *Vampire Survivors* / *Brotato* with a **cyberpunk** theme. Built in **Godot 4.7** with GDScript. Originally aimed at Android, but it now **runs on Windows/desktop** too (keyboard + mouse; `export_presets.cfg` has a Windows Desktop preset). The whole UI is keyboard-friendly with **rebindable keys** and a **Settings** page (volume + controls).

## Game concept
- Top-down arena. The **player** appears centered (a `Camera2D` follows them) but moves freely across a large world.
- **Enemies** spawn continuously from off-screen and chase the player. They **stop at the edge of the player's sprite** instead of walking over them — by distance, in code, never by physics collision, so they neither clump into each other nor shove the player.
- The player **auto-fires** projectiles at the nearest enemy. Enemies have HP and die.
- Enemies touching the player deal **contact damage**; the player has HP + a health bar.
- **Roguelike core:** dead enemies drop **XP** → XP bar fills → **level up** → choose **1 of 3 items/upgrades** (weighted by rarity). Difficulty ramps over time (enemies faster/tougher/hit harder, drop more XP). **51 upgrades** with real effects and hidden synergies. Playable in **9 languages** (flag button in the menu).

## Tech & conventions
- **Engine:** Godot 4.7 stable · 2D · "Mobile" renderer (the name is just a rendering method — it runs fine on **Windows/desktop** too, keyboard-controlled; `export_presets.cfg` has a Windows Desktop preset). Stretch mode `canvas_items`, aspect `expand` (scales to any screen).
- **Language:** GDScript. **All on-screen text is written in English in the code** — English is the source language, and the other 8 come from `i18n.gd` (see *Languages* below). Never write a display string in Romanian.
- **UI font:** the whole UI uses a single global font, `menu/HomeVideo-Regular.otf` (a pixel font), set via `project.godot` → `[gui] theme/custom_font`. UI code only ever overrides font *size*/*color*, never the family, so this default font applies everywhere. Its `.otf.import` must be committed (a standalone run can't load an un-imported font — run `--headless --import` after adding fonts). The font covers Latin (with Polish/Turkish diacritics) **and Cyrillic**; Chinese and Japanese have no glyphs in it and are drawn by the **system fallback** (`allow_system_fallback=true` in the `.import`), which is why they render in a different, non-pixel typeface.

## Languages (9)
The game ships in **English · 中文 · Deutsch · Español · Русский · Français · 日本語 · Polski · Türkçe**, picked from the **flag button** left of the ⚙ gear in the main menu. The choice is saved (`GameSettings.language`) and applies **instantly**, without a restart.

- **Everything lives in `i18n.gd`** (autoload `I18n`): one `TRAD` dictionary, key = the English string exactly as written in the code, value = the 8 translations in the order of `ORDINE`. At startup it builds one `Translation` per language and hands it to `TranslationServer`.
- **The game code barely changed**, because Godot **auto-translates** any text put on a `Label`/`Button`. Assign the plain English string and it comes out translated — and re-translates itself when the language changes.
- ⚠️ **The one exception is formatted text.** `"Kills: %d" % n` produces `"Kills: 42"`, which matches no key, so those must be written **`tr("Kills: %d") % n`** — see `hud.gd`, `gameover.gd`, `interact_ui.gd` and the leaderboard row in `menu.gd`. For the same reason, **never `tr()` a plain label**: the translated string would be stored on the node and would stay in the old language after a switch.
- **Adding a string:** write it in English in the code, add a row to `TRAD`. **Adding a language:** add its code to `ORDINE`, a row to `LIMBI`, one more translation on **every** `TRAD` row, and a flag in `menu/flags/`.
- **Flags** are 24×16 pixel-art PNGs drawn from code by `tool_flags.gd` (`godot --headless --path . --script res://tool_flags.gd`) — no downloaded images, no licence questions, and they can be regenerated at any size.
- **Check it before committing:** `godot --headless --path . res://tool_check_i18n.tscn` verifies that every row is complete, that every upgrade name/description in `levelup.gd` and every `tr(...)` in the code has translations, and lists any display string that has none. It exits non-zero on a real gap.
- **Indentation: TABS.** Godot rejects mixed tabs/spaces — this is *the* most common error when pasting code. After any paste use **Edit → Convert Indent to Tabs**.
- **Groups** are used to find nodes across the tree: the player is in group `"player"`, enemies in group `"enemy"`. Look up with `get_tree().get_first_node_in_group("player")` and `get_nodes_in_group("enemy")`.
- `get_*_in_group` returns a generic `Node`, so **cast with `as Node2D`** before touching `global_position` (otherwise "cannot infer type" errors). Dynamic property access on such nodes yields harmless **yellow** warnings (yellow = warning/OK, red = error/must fix).
- **Groups used for combat:** on top of `"player"`/`"enemy"` there is **`"boss"`** (the Garda and Saratalin join it in their `_ready()`). It exists so effects that would trivialise a boss fight can opt out in one place — right now that is the Hacksaw instakill, skipped in both `bullet.gd` and the sword pass in `player.gd`.

## The upgrade codex (published page)
There is a **codex of every upgrade**, kept as `codex.html` in the repo and published as a private page on claude.ai: <https://claude.ai/code/artifact/490e047c-2f80-45c5-b6a6-9af326065a4e>. It opens with **Statusuri de start** *(2026-07-28)* — what the player has at second 0, in two tables: the four weapons (damage / attack speed / what actually lands on the enemy) and the eleven stats that are identical whichever weapon you pick. Those numbers are **not read off the source**; they come from running the game — a throwaway scene instantiates the player once per weapon and prints `stat_lines()`, the very rows the level-up panel shows, with `GameSettings.upgrades` emptied **in RAM only** so the permanent shop is out of the picture (the save file was checksummed before and after to prove it stayed untouched). Anything that changes `speed`, `max_hp`, `contact_damage`, `xp_to_next`, the `ARME` table, `aura_damage` or `sword_base_damage` silently makes that section wrong. Each card shows **two** rows: **ÎN JOC** — the exact string the player sees on the level-up card, and **CE FACE DE FAPT** — what the code actually does, read out of `_apply()` in `levelup.gd` and `player.gd`. The first row is **generated from `levelup.gd`**, never typed by hand, so it cannot drift; a script re-derives all 47 and a second script checks them character for character.

⚠️ **The whole page is built by JavaScript, so one bad character blanks it completely, with no error anywhere.** That happened: a Romanian closing quote written as a plain `"` ended a string early and the page shipped empty. **Always render it before publishing:**

## Project structure
All scenes (`.tscn`) and scripts (`.gd`) live in the project root.

- **`menu.tscn`** (`Control` + `menu.gd`) — the main menu (main scene): animated background, weapon/character pick, Leaderboard, a **⚙ Settings** page (top-right gear) with **Music/SFX volume sliders** and **key rebinding**, and a **flag button** next to the gear that opens the **LANGUAGE** page (9 languages). All built in code. *(The `UPGRADES` shop page was removed on 2026-07-27 — see that session log.)*
- **`i18n.gd`** (autoload `I18n`) — the translation table for all 9 languages, plus `menu/flags/*.png`. See *Languages* above.
- **`main.tscn`** — the game world (root `Node2D` "Main"):
  - `Ground` (Sprite2D + `ground.gd`) — the infinite repeating grass that follows the player.
  - `World` (Node2D, `y_sort_enabled`) — depth-sorted container holding `Props` (trees), `Rocks` (stones), `Player`, and (added at runtime) the enemies, so they overlap correctly by depth.
  - `Props` (`props.gd`) / `Rocks` (`rocks.gd`) / `DesertStructures` (`desert_structures.gd`) — chunk-based procedural, deterministic spawners (infinite). Rectangle hitboxes with per-side tuning (`hitbox_north/south/east/west`), `sort_anchor`, `min_gap_hitboxes` (min spacing). **Biome rules:** trees avoid the desert *and* its soft gradient; rocks avoid only the hard desert (they may sit on the gradient); desert structures (cactus/house/monument) spawn *only* in the desert — see `BiomeMap.is_desert_chunk` / `desertness_at_chunk` / `desert_inset_chunk`.
  - `Spawner` (Node + `spawner.gd`) — a Timer that instances enemies **all around** the player (into `World`), inside a cone of ±`spawn_cone_deg` around the facing direction — **180° = the full circle since 2026-07-28** (it was 45°, "front only", between 2026-07-22 and then). Distance is `_distanta_spawn()` = `max(spawn_distance, screen half-diagonal + spawn_margin)`, so they are always born off-screen.
  - `Portals` (`portals.gd`) — same chunk-based deterministic spawner, `portal_chance` **1.5%** (twice as rare as statues), kept clear of trees/rocks/statues. Each portal is `portal.tscn` + `portal.gd`; art **and** hitbox are tuned **by hand in the editor**, exactly like the statue — the script never touches either at runtime.
  - `Chests` (`chests.gd`) — treasure chests placed **beside the dirt paths**, 20px from the path edge, on **35% of paths** (measured 35.1%). See the `chests.gd` entry below.
  - `EGTs` (`egts.gd`) — the **EGT slot cabinets**, another chunk-based deterministic spawner (`egt_chance` **2%**, rarer than statues), kept clear of trees, rocks and statues. Each one is `egt.tscn` + `egt.gd`; press E to open the casino. See the `casino.gd` entry below.
  - `Monuments` (`monuments.gd`) — the **monument** spawner *(2026-08-05)*, a fourth chunk-based deterministic generator: `monument_chance` **1%** of chunks (rarer than statues at 3% and portals at 1.5%), kept clear of trees, rocks **and statues**; measured 0.94% over 10,000 chunks. Each one is `monument.tscn` + `monument.gd`. Unlike the other generators it **remembers the ones you used** (`_folosite`), so a monument you awakened does not come back when its chunk unloads and reloads. See the `monument.gd` entry below.
  - `EnderStatues` (`ender_statues.gd`) — the **Ender trading statues** *(2026-08-05)*, and the **only generator that runs backwards**: it ships **disabled** (`visible = false`, `process_mode = 4`) and is switched **on** exactly while you are in the Ender, by the same `ender.gd` call that switches all the others off. That is why it is in `ENDER_ONLY_NODES` and *not* in `WORLD_NODES` — listed there it would do precisely the opposite of what it is for. It is also **not chunk-based**, unlike every other generator here: it drops `numar` (**3**) statues in a **ring 600–2000 px around the well you arrived through** (`ender.gd::portal_pos()`), the moment the Ender opens. It was chunk-based for a few hours on the day and that was wrong for the job — chunks scatter forever, so a statue could land 30,000 px away, somewhere you will never reach inside six minutes. A ring is a rule about *distance from a point*, so it is written directly instead of filtered out of a generator, and you always get exactly three instead of sometimes none. They keep `dist_intre` (520 px) from each other. See the `ender_statue.gd` entry below.
  - `Casino` (CanvasLayer + `casino.gd`) — the **"Let's go gambling"** screen the EGT opens. See its entry below.
  - `Trade` (CanvasLayer + `trade.gd`) — the **ENDER TRADE** table the Ender statue opens. See its entry below.
  - `Nether` (CanvasLayer + `nether.gd`) — the **second dimension**. Press E at a portal and you're taken there; see the *Nether* section below.
  - `HUD` (CanvasLayer + `hud.gd`) — screen-fixed UI: health bar + XP bar + level, all built in code.
  - `Pause` (CanvasLayer + `pause.gd`) — the **ESC pause menu**: pauses the run and shows *Resume · Main Menu · Restart Run · Settings · Quit Game* (ESC again resumes). Its Settings page reuses the same **`settings_ui.gd`** (`SettingsUI`) block as the main menu — one copy of the logic, used in both places. `SettingsUI` has **two tabs** *(2026-07-26)*, switched by a button bar at the top (the open one is lit): **KEYBINDS** (music/SFX sliders + key rebinding, i.e. everything that was there before) and **GRAPHICS** (`FULLSCREEN`, `V-SYNC`, `VIGNETTE`, `GLOW` — ON/OFF buttons). All four are saved in `GameSettings` and re-applied at launch by `aplica_grafica()`; vignette and glow are owned by `atmosphere.gd`, which only exists in-game, so changing them from the main menu takes effect when the run starts (the page says so) while the pause menu shows it instantly. Switching tabs cancels a rebind left waiting, so the next key you press is not swallowed by it. Won't open over Level Up / Game Over. **All sound freezes with it** (`Audio.pause_all()` / `resume_all()` — music, forest ambient and any SFX still ringing keep their position and continue on Resume); menu clicks are the exception and stay audible.
  - `LevelUp` (CanvasLayer + `levelup.gd`) — the level-up choice screen (3 of **47** upgrades, **weighted by rarity**), styled like *Megabonk*: an ornate `Menu.png` panel with each choice framed by a **rarity border** (Common→Legendary) + matching colored text; pauses the game.
    - ⚠️ **Rarity is a real drop rate, not just a colour** — `RARITY_CHANCE` at the top of `levelup.gd`: Common 40 · Uncommon 35 · Rare 15 · Epic 7.5 · Legendary 2.5. The roll picks the **rarity first**, then an item within it, so **how many items a tier holds no longer changes how often that tier appears** — adding a Legendary keeps Legendary at 2.5% and simply splits it further. (Before this, selection was uniform over the whole list, which made Legendary show up in 11.4% of rows.) Each entry is one dict in `UPGRADES` (id / name / icon / rarity / description) and its real effect is a `match` arm in `_apply()` — **the description text is not the source of truth, `_apply()` is.**
  - `GameOver` (CanvasLayer + `gameover.gd`) — the **"YOU DIED"** screen (`layer = 20`, above everything): time survived, level reached, kills, plus *Play Again* and *Menu*. Built entirely in code. Its backdrop is a **fully opaque black** `ColorRect` *(2026-08-05, was 80% black — the frozen world used to show through)*.
- **`player.tscn`** (`CharacterBody2D` + `player.gd`) — has an **AnimatedSprite2D** (8-directional run + idle poses, `player_frames.tres`), CollisionShape2D, Camera2D. Handles keyboard movement (**WASD + arrow keys, remappable** in the Settings screen — reads the `move_up/down/left/right` actions defined at runtime in `game_settings.gd`), auto-fire at nearest enemy (Timer), HP + a contact-damage tick, the fire trail (Firewalker), and death (opens the Game Over screen).
- **`enemy.tscn`** (`CharacterBody2D` + `enemy.gd`) — chases the player, has HP, `take_damage()`, dies via `queue_free()`. Uses an **AnimatedSprite2D** with **8-directional walk animations** (`enemy_frames.tres`, 6 frames each, picked by angle in `enemy.gd`'s `DIRECTII`); the art lives in `homeless directii/frames/` (a **police officer** since 2026-07-27 — the folder name is historical).
- **`enemy_police_skinny.tscn`** *(2026-08-05)* — the **second overworld officer**, same `enemy.gd` but faster (160), tougher (45 HP) and hitting a bit harder (`damage_mult` 1.3). Its frames are built at runtime from `homeless directii/Police Skinny/frames` (6 per direction). `spawner.gd` starts mixing it into the police after **1:00** (`skinny_after` / `skinny_share`).
- **`bullet.tscn`** (`Area2D` + `bullet.gd`) — flies in a direction, on `body_entered` damages bodies in group `"enemy"`, self-destructs after `lifetime`. Supports **pierce**, **knockback**, **crit**, and **explosive AOE** (Jean's Bomb).
- **`firetrail.gd`** (script-only, instanced from `player.gd`) — a fire patch dropped at the player's feet while moving (**Firewalker** upgrade): plays the fire animation, burns enemies in range on a tick, rotates to the movement direction, renders **under** the actors (`z_index`), and fades after a per-stack duration.
- **`interact_ui.gd`** — a **"Press E to interact"** prompt (grey, game font) that floats **above the nearest interactable object** in range (world position → screen via `get_canvas_transform`, so it sits over the object and stays above the world y-sort). Pressing the rebindable **`interact`** action (default **E**, shown live in the text) calls `invoca()` on it. **(2026-07-26)** It iterates the **`"interactable"`** group (was `"statue"`) — anything that joins it and exposes `interact_range` / `poate_invoca()` / `invoca()` gets the prompt for free. Statues, portals and chests all do. **(2026-07-27)** An object may also expose **`eticheta()`** to replace the prompt text with its own (the locked chest returns "You need a key"), and **`label_offset_y`** to say how high the text should float above it. **The prompt is drawn at font size 14 with a 3px outline** *(2026-07-27, halved from 28/6 on request)* — the outline had to come down with the font, or at 14px it would be thicker than the letter strokes and the text would read as a black smear — a 260px statue and a 90px chest do not want the same offset; without it the default `world_offset_y = -175` still applies. (Replaced the old phone-style screen SUMMON button.)
- **`statues.gd`** — spawns statues procedurally, chunk by chunk like trees and rocks: **3% of chunks get exactly one**, at a deterministic position that keeps clear of nearby trees **and rocks** (crowded chunks simply get none, costing ~0.4%). Every run also **starts you at a random point** in the infinite world (`spawner.gd`, saved to `GameSettings.run_spawn`), so the map is different each time without touching the generation math.
- **`statue.tscn`** (`StaticBody2D` + `statue.gd`) — an interactive world statue with a **visually-editable** collision box. Its look is rolled at spawn from three variants (`harta/Statue Version 1..3.png`) with weights **60% / 30% / 10%** — edit the `VARIANTE` list at the top of `statue.gd` to change the odds. When the player is near, a small **"Summon"** button appears. Pressing it plays a one-shot sequence: alert symbol → statue **sinks into the ground** (its collision disables) → **screen shake** (camera-offset earthquake) → a **boss rises slowly from the ground**. All timings/offsets are `@export`.
- **`monument.tscn` + `monument.gd`** *(2026-08-05)* — the **Monument**, a stone obelisk (`harta/Monument Spawner.png`) that stands in the normal world and is **locked until Celesto is dead**. While `Ender.celesto_invins` is false the prompt above it reads **"Defeat Celesto to awaken it"** and `invoca()` refuses — the locked-chest trick: it stays interactable so it still has a label, instead of looking like scenery. Press E once Celesto has fallen and it pours out a **horde of 103**: **100 enemies picked at random from all four kinds** (police · Police Skinny · Nether creature · Ender creature, equal weights in `FELURI`) plus **3 Gardas**, the statue boss, rising from the ground. Everything it spawns gets three changes, measured against an enemy born *at that same moment*: **×2 XP** (`enemy.xp_drop_mult`, a new `@export` applied in `_drop_xp`), **×3 speed** (set before `add_child`, because `enemy._ready()` bakes the final speed there) and **×3 contact damage** (`damage_mult`, so it stays *relative*: the Ender creature's 2.0 becomes 6.0). The Gardas get the same, plus **×3 lightning damage** and **×2 XP value** — `garda.gd` gained its own `damage_mult` export (default 1.0, so the statue's Garda is unchanged). They do not arrive all at once: they trickle out **one at a time, evenly, over `spawn_duration` (10 s)** — one every ~0.097 s — in a **620–1150 px ring** around the monument, added to `World` rather than under the monument, whose chunk container is freed when you walk away. The obelisk stays standing while it pours, then **sinks and is gone for good** — `monuments.gd` records its chunk, so it does not respawn when the chunk reloads. The pacing loop asks *"how many should be out by now"* once per frame instead of chaining waits, so a slow frame gets caught up instead of being added to the tail; its clock is summed from frame deltas and **stops while the tree is paused**, because a 10-second horde almost always overlaps a Level Up screen — on a wall clock the rest of the horde would dump in a single frame on Resume. The 3 Gardas sit at 1/6, 1/2 and 5/6 of the queue (≈1.6 s, 5 s, 8.3 s), so none of them lands on the frame that already pays for the alert symbol and the shake. Verified by running: 100 + 3 spawned, speed ratio 3.001–3.002, XP gem 2 → 4, Garda 210 speed / 45 lightning / 100 XP; first at 0.02 s, last at 9.90 s, **11·10·10·11·10·10·11·10·10·10 per second**, never more than **1** in one frame, and a simulated 2-second pause at t=3 s left the schedule untouched. Longest frame of the whole invocation: **19.5 ms** — but only if the test scene runs `PreloadAll` first, exactly as a real run does; without it the alert symbol's 16 PNGs are read from disk and the frame looks like ~140 ms, which is what an earlier measurement here wrongly blamed on the game.
- **`ender_statue.tscn` + `ender_statue.gd` + `trade.gd`** *(2026-08-05)* — the **Ender statue**, the hooded stone monk (`harta/Ender Statue.png`) that only exists **inside the Ender**, and the **ENDER TRADE** table it opens. Press E and it shows **3 of your own items**, drawn at random from the run's ledger whatever their rarity, each with an arrow to **what it can become: an item two rarity steps up** (`levelup.gd::raritate_mai_sus`, clamped at Legendary — so Common→Rare, Uncommon→Epic, Rare→Legendary, and an Epic or Legendary trades for a Legendary). Pick a row and the swap is instant. **The price is difficulty, not gold**: every trade multiplies `Difficulty.trade_penalty` by 1 + `cost_procent`/100 (**+15%**), and that factor goes into enemy HP, contact damage, spawn rate and speed — so the menu's "COST: +15% DIFFICULTY" is literally true on all four. *(It was +15 **seconds** on the enemy clock for a few hours on the day, which was worth +8.8% HP but only +2.6% spawn and +0.7% speed — different percentages per stat, thinning out as the run went on. A label reading "15%" over that would have been a lie, so the mechanic moved to match the label, not the other way round.)* It deliberately does **not** touch `Difficulty.time`, the clock on screen and in the leaderboard — otherwise a trade would shorten your run and **pay you score you never survived** — and it does not touch `xp_mult` either, because a cost that also pays you back is half a cost. At speed it is applied **before `SPEED_CAP`**, so the cap still wins: ten trades leave enemies at 2.2× and no faster. Measured: 1 trade = +15.0% on all four, 2 = +32.2%, 3 = +52.1%, XP +0.0%, run clock untouched. **One trade per statue**, then it dims and goes quiet — without that limit there is no natural stop, because every trade hands back exactly one item and leaves the ledger the same size. ⚠️ **What a trade does *not* do is take the old item's effect back.** Effects are applied once, at pickup, straight onto stats (`levelup.gd::_apply`), and nothing in this game has ever removed one — half of them couldn't be (Panic Button already exploded, Wine already healed you). So the item leaves the **ledger**, not your stats, and a trade is a clean gain paid for in difficulty. Undoing that means writing an "unapply" for all 50 items. The ledger itself is new: **`player.run_items`**, filled from the single choke point `_apply`, so level-ups, chests and the statue's own payout all land in it. **The screen itself is built from `harta/Border Statuie Ender.png`** — a 5×4 sheet of 64×64 crimson frames, from which `trade.gd` cuts only the cells it needs at runtime (`_chenar`): cell (2,0) for the outer frame, (1,2) for each offer row. The friendly gold `Menu.png` is gone; the panel is near-black with one accent colour, the cost reads **"COST: +15% DIFFICULTY"** in blood red, and **"You can only choose one"** sits under it. Hovering a row pulls its frame from ash-grey back to full crimson in 0.12 s — an alpha-only version (0.45 → 1.0) was invisible on a screenshot, because crimson still reads bright on black at 45%. The item you **give** is held at 70% opacity and the one you **receive** at 100%, so the direction of the deal is legible without labelling it. Two traps worth remembering, both caught by screenshotting rather than by reading code: the panel must fit **1152×648** (the base resolution Godot draws at before stretching — the first version was 672 tall and had its top and bottom corners off-screen), and a nine-patch stretches the *middle* of an edge, not its thickness, so a 64px cell on a 940px panel leaves 1px lines — the cell is upscaled ×2 nearest-neighbour first, with `patch_margin` scaled to match. Its backdrop is a **fully opaque** `ColorRect`, not the casino's 0.985 — at 98.5% the Ender's 64px cyan clock still bled through the top of the panel as a ghost and read as a rendering bug. Verified by running, end to end inside a real Ender entry (well + Celesto cutscene, spawner off so nothing can kill the player and write a fake leaderboard score): ledger empty at start and exactly 7 after 7 pickups, "Nothing to trade" while empty, rows measured at +2 rarity steps, the traded item gone / the new one present / the ledger the same size, `trade_penalty` 1.00 → 1.15 on a real button press with `Difficulty.time` untouched, the statue spent and the table closed and the game resumed, a second press doing nothing, and `reset_run()` clearing the penalty.
- **`portals.gd` + `portal.tscn` / `portal.gd`** *(2026-07-26)* — a stone-arch **Portal** (`harta/Portal 1.png`), spawned exactly like statues but **rarer**: `portal_chance = 1.5%` of chunks vs the statue's 3%, with its own `SEED_SALT` so it never lands on the statue's roll. ## Weapons
**Four to pick from**, in the main menu (`GameSettings.weapon_type`, read by `player.gd` on `_ready`): Pistol, Mage Staff, Cursed Sword, Celesto's Scythe. `weapon_type` decides both the starting numbers (the `ARME` table) and the *behaviour*, the latter in a handful of places in `player.gd`:

**The player walks at `speed = 215`** *(2026-07-27)* — it was 300, halved to 150 on request, then raised twice in the same session. Where that lands: the police start at 120 and gain 3.5%/min, so they only pass you at **~12:36** (deep in Final Swarm) and cap at 264, **1.15×** your speed; the Nether creatures start at 190 and pass you at **~6:06** of run time, capping at 418, **1.82×**. In short: **in the world you can outrun them, in the Nether you cannot.** (Measured with the game's own math on a save with Speed level 1, i.e. 230.)

**Each weapon now trades damage against rate of fire** *(2026-07-27)* — before this they all started identical (10 damage, one hit every 0.5 s) and differed only in *how* they hit. The numbers live in one table, **`ARME` at the top of `player.gd`**, applied by `_aplica_arma()` **before** `_apply_meta()` so shop upgrades stack on top of the weapon instead of being overwritten:

| Weapon | Damage | Interval | Hits/s |
|---|---|---|---|
| **Pistol** | 15 | 0.75 s | 1.33 |
| **Mage Staff** | 10 | 0.50 s | 2.00 (**1.5× the pistol**) |
| **Cursed Sword** | 20 | 0.75 s | 1.33 |
| **Celesto's Scythe** | 24 | 0.95 s | 1.05 (**the slowest**) |
| **Throwing Knife** | 12 | 0.55 s | 1.82 (**the fastest**) |

*(The **Extinguisher** was the fifth entry here until 2026-08-04, when it was removed from the game on request — see the section below. The sword inherited its sound.)*

**Every weapon also grows with your level** *(2026-08-05)* — a bonus that is not an item and cannot be lost:

| Weapon | Per-level bonus | Where it lives |
|---|---|---|
| **Throwing Knife** | +1% crit chance | `crit_chance_now()` |
| **Cursed Sword** | +1% damage | `damage_mult()` |
| **Pistol** | +1% attack speed | `fire_interval_now()` |
| **Celesto's Scythe** | +1% weapon size | `weapon_size_scale()` |
| **Mage Staff** | +1 Luck | `luck_total()` |

Counted **from level 1**, so level 12 means +12%. Nothing is written into a stat — it is computed at use, like `damage_mult()`: writing it in would mean subtracting the old bonus and adding the new one on every level-up, and it would break silently the first time an upgrade multiplied that stat. The knobs are `BONUS_PE_NIVEL` and `LUCK_PE_NIVEL` in `player.gd`; the strings under each weapon in **CHOOSE WEAPON** are written by hand in `menu.gd::WEAPONS` and will lie silently if you change the numbers without changing them.

⚠️ **That "damage" is the `bullet_damage` stat, not always what lands.** The sword adds `sword_base_damage` whole (8 + 20 = **28** per slash) and the scythe adds `scythe_base_damage` (12 + 24 = **36** per sweep). ⚠️ **`sword_slow_start` is gone** — the sword used to swing at 1.9× the interval; Răzvan asked for pistol cadence, so its drawback is now its reach, not its speed.

| Weapon | How it fires |
|---|---|
| **Pistol** | One bullet at the nearest enemy. Nothing else. Its bullet is **capped at 100%** — size upgrades do not grow it (`BULLET_SIZE_CAP`). |
| **Mage Staff** | The same bullet, re-skinned as an animated orb, that **explodes on impact** (radius 110, damage = 60% of `bullet_damage`). Its orb grows with size upgrades but is **capped at 250%**. |
| **Cursed Sword** | No bullets — a **melee slash** in the direction you're **facing** (`_facing`), hitting *every* enemy whose **body circle touches** a fixed rectangle that runs from the player out to the animation's furthest pixel, for `sword_base_damage + bullet_damage`. (Circle, not centre point, since 2026-07-28 — that is what made it useless against Saratalin.) Built on the **Firewalker model**: `sword_size` is the width in px, and the rectangle is *measured from the art* at startup, so art and hitbox cannot drift apart. Swings at the **pistol's cadence** since 2026-07-27 (the old `sword_slow_start` 1.9× handicap was removed on request). The slash animation is a **child of the player**, so it follows you (feels like the sword is always in hand), and draws **under** him. Scales with damage / crit / knockback / instakill / weapon-size upgrades. |
| **Throwing Knife** | *(2026-08-05)* The same bullet again, re-skinned as the **knife icon itself, spinning in flight** (`bullet.gd::spin` turns the *sprite*, never the node — the node's rotation is the flight direction). Not a new bullet scene: reusing `bullet.tscn` means it inherits pierce, ricochet, homing, Thunder God and Jean's Bomb for free, and there is no second place to keep up to date. No muzzle flash (there is no barrel) and it uses the sword's blade *swish* instead of the gunshot. Capped at **150%**. |
| **Celesto's Scythe** | No bullets — the boss's own blade sweeps a **full circle around you** every `fire_interval`, for `scythe_base_damage + bullet_damage`. Short fixed reach (130 px to the tip) but it cuts on **every** side, and it hits each enemy **as the blade reaches them**, not all at once — the turn starts behind you so the blade crosses your facing first. The hitbox **is the drawing**: a distance field measured from the art at startup, grown by `scythe_marja` (5 px). The blade's axis is measured from the art too (principal axis of its pixels), so it lies along the radius instead of pointing off-angle. `scythe_debug` draws a ring on whoever is under it right now. |

**Collision:** everything is on the default layer/mask (layer 1). Bullets (Area2D) detect enemies (CharacterBody2D) via `body_entered` and filter with `is_in_group("enemy")`, so no manual collision-layer setup is needed yet.

## Current state (2026-08-07, the Ender sky rebuilt: the straight blue lines were the HASH)
- 🩹 **The bug:** long straight lines swept across the Ender, rotating slowly. Not the nebula, not the stars — `hash21`, the `fract(fract(...))` hash both dimension shaders were built on. Interpolated noise is continuous **only if two neighbouring cells read exactly the same value at the shared corner**, and that hash ends by multiplying two numbers around ~90 (product ~8600), where a `float`'s step is ~0.001. The shared corner came out slightly different from each side → a step in value → a dead straight line on the cell boundary. Replaced with the integer bit-hash already used by `biome.gdshader`, plus **quintic** interpolation. The rule worth keeping: **for full-screen noise, hash on integers, never `fract()` over `fract()`.** ⚠️ `nether_hell.gdshader` still has the old one — its smoke has the same disease.
- 🌌 **And the sky was rebuilt around it.** Domain-warped nebula with dust lanes cutting through it (the one thing that stops a procedural cloud looking procedural); **three star layers** with power-skewed brightness (few bright, many faint), cool/amber colour variation and a thin light cross on the brightest few; an aurora whose bend comes from noise rather than a clean sine; a shooting star every ~19 s; a softer vignette. ⚠️ A star's offset inside its cell is ±0.25 and its halo dies by 0.25 too — anything that reaches the cell edge gets cut flat, which is the very straight edge being fixed here.
- 🛰️ **Parallax — the biggest single change.** `atmosphere.gd` now feeds the shader `world_offset` = `-canvas_transform.origin` every frame (screen pixels, camera zoom already baked in, so no Camera2D lookup). The sky drifts behind you at 0.020 / 0.055 / 0.115 per layer. Before this it was welded to the screen and read as *a filter over the game*; now it reads as *a place*.
- 🎚️ **Dither, 1/255 per pixel, before output.** Very dark gradients otherwise band into rings on 8 bits. It is one line and it is most of the difference between "shader from a tutorial" and a finished game.
- 🔬 Verified by running: the shader alone at three world positions (no straight edges anywhere, a different sky at each); then through the real path (`set_dimension("ender")`) over a fake world and a fake HUD, which stays legible; and **measured on the GPU at 1920×1080 with vsync off — 1.487 ms without the shader, 1.711 ms with it, i.e. 0.225 ms.** Cheap, but measured, because this is an Android project.

## Current state (2026-08-04, the scythe's hitbox *is* its drawing, grown by 5 px)
- ✅ **Fixed on report** ("hitboxu la scythe nu e egal cu sprite-ul in sine, poti chiar sa il faci cu 5pixeli peste sprite"). - ⚠️ **The fix exposed a bug that was invisible before:** the blade was placed along the *image's* Y axis, but the scythe is drawn diagonally, so it pointed about **40° off** the ray the sweep was damaging along. Measured: the enemy directly behind you — where the sweep *starts* — was hit **last**, a full turn later. The axis is now measured from the art.
  - Not the centroid of the drawn pixels: for this scythe it lands almost exactly at the image centre, so its direction is pure noise (tried it — still 40° off). It is the **principal axis** (scatter matrix, `theta = ½·atan2(2·Sxy, Sxx − Syy)`), i.e. the direction in which the drawing is longest.

## Current state (2026-08-04, the outline is one *screen* pixel, drawn by a shader)
- ✅ **Celesto and its scythe now wear a 1-pixel outline — measured on the screen, not in the file.** It was already 1px before, but 1px *of the source image*, and the boss is drawn at `scale = 3.2`, so what you actually saw was a 3-pixel border. There is no thinner baked answer (you cannot draw half a pixel), so the outline moved out of the PNGs and into **`contur_1px.gdshader`**, set on the `AnimatedSprite2D` in `celesto.tscn` and the `Sprite2D` in `scythe.tscn`. `celesto.gd` reads `frames/` now instead of `frames_contur/` — otherwise you would get the 3px baked border *plus* the new one.
- **The shader learns the pixel size from the UV derivative** (`dFdx`/`dFdy`): how much UV changes when you move one pixel across the screen, right there. So the thickness stays 1px at any sprite scale and any camera zoom — which also settles the phase-3 **giant scythe** for free: a baked outline would have been tripled along with `marime`, and the two scythes would have stopped reading as the same weapon.
- ⚠️ **Not `fwidth`**, even though that is the reflex. `fwidth = |dFdx| + |dFdy|`, and the scythe **spins in flight** — on the diagonal that sum overshoots by up to 40%, so the outline would have fattened as it turned. It uses the per-axis gradient length instead.
- ⚠️ **`MODULATE` does not exist in 4.7's canvas shaders** ("Unknown identifier in expression"), and inside `fragment()` the built-in `COLOR` already has the texture multiplied in, so you cannot recover the node's modulate from it. A `varying` written in `vertex()` carries it across. This matters: without it the outline would stay lit over a boss that is fading out on death, and it would ignore the white hit-flash.
- Verified on a run: across 60 scanlines through Celesto, **379 outline bands exactly 1px wide**; the 6–7px ones are *horizontal* edges, where the scanline travels **along** the outline instead of across it. The small scythe and the 3× one come out equally thin, which is the whole point — the outline does not scale with `marime`.

## Current state (2026-08-03, the Nether burns and the Ender goes cosmic)
- ✅ **Both pocket dimensions now have a look of their own**, on request: the Nether reads as **hell** (deep ember red, sparks rising, smoke, a furnace glow from below), the Ender as **space** (cold blue-violet, twinkling stars over a slowly rotating nebula, an aurora ribbon, a deep indigo void at the edges).
- **It is two mechanisms, not one, and that split is the whole design.** The **colour** of the place comes from a **`CanvasModulate`** (`atmosphere.gd::DIM_TINT`), which only touches the ordinary canvas — so the world is tinted and the **HUD is not**. A full-screen shader doing the grading would have turned the health bar, the XP bar and the clock red along with everything else. The **motion** — sparks, stars, haze, vignette — comes from a screen overlay: `nether_hell.gdshader` and `ender_cosmic.gdshader`.
- ⚠️ **Neither shader reads the screen** (`hint_screen_texture`), unlike `limbo_bw.gdshader`. That is why they can sit above the HUD without smearing or desaturating it: they only *add light*. Both end with the same single-pass composite — alpha is `vignette + brightness of the light`, and the colour is divided by that alpha so the blend multiplies it back. Accepted consequence: strong light covers the background, which is exactly what you want from a spark.
- **One entry point:** `atmosphere.gd::set_dimension("nether" / "ender" / "")`, called with a single line from `nether.gd` and `ender.gd` next to `_set_ground_*`. Everything about "how the other side looks" lives in one file.

It was on in the Nether too at first; Răzvan asked for it off the same day — *"I don't want the screen moving weirdly"* — and the reason is the art, not the numbers: **brick has long straight lines**, so any warp on them reads as the screen moving rather than as heat haze. ## Current state (2026-07-30, enemies walk around obstacles)
- ✅ **An enemy that jams into a tree, a rock or a statue now steps aside instead of pushing into the hitbox forever.** `enemy.gd` compares the **real** per-frame displacement with the requested one; under 40% for 0.15s means it is getting nowhere, and the walk direction is rotated **80°** for 0.6s before resuming the chase. Not pathfinding, on purpose — the world is infinite and chunk-generated, and 300 enemies running A* per frame would kill the framerate.
- The side comes from the collision normals (the tangent that points more towards the target = the short way round). Head-on, both sides are equal, so `get_instance_id() % 2` decides — arbitrary but **constant per enemy** (no jitter) and different between them (two enemies stuck on the same tree do not both go left).
- 🐛 Two failure modes worth remembering, both caught by the test: **re-picking the side on every re-block** (and flipping "to try the other one") makes the enemy sway up and down the face of the obstacle forever, and **committing to one side blindly** parks it in a dead-end corner. What works is: keep the side until it actually gains ground, and if 2s of avoiding does not bring it 40px closer, try the other side **with double the patience** (2s → 4s → 8s), which is what gets it around a long wall.

## Current state (2026-07-28, 5G Tower — and the XP bug it uncovered)
- ✅ **5G Tower** (Epic, `upgrade_58`) — `xp_gain_mult += 0.15`, reusing the multiplier the permanent shop already fed. It **adds** to the shop's "XP gain" levels rather than multiplying with them, and it catches **all** XP that comes in, not only what enemies drop (Borat's Mankini gems included) — the card says "enemies", the code is broader.
- 🐛 **The item would have done nothing, because of a bug that was already there.** `gain_xp()` did `xp += int(amount * xp_gain_mult)`, and `int()` **truncates**. The small XP gem is worth **1**, so `int(1 × 1.15) = 1`: any XP bonus under +100% was invisible on exactly the gems you pick up most. That silently applied to the shop's **XP gain** levels too (+8% each, up to +64%). `gain_xp()` now banks the sub-1 remainder in `_xp_rest` and pays it out on the next gem — at +15%, the seventh 1-XP gem is worth 2.
- ⚠️ It also carries a `+ 1e-9`: 1.15 has no exact binary form, so twenty gems summed to 22.999999… and `int()` returned **22 instead of 23**. The point was not lost (it stayed in the remainder) but the totals stopped matching what a player would work out on paper. Caught by running it, not by reading it — the first test run printed 22.
- Verified on a real run: `xp_gain_mult` 1.00 → 1.15 → 1.30 on a second pick (it **adds**); twenty 1-XP gems at +15% gave **23** (was 20); five 10-XP gems gave **57** (= 50 × 1.15).

## Current state (2026-07-23, poteci în pădure)
- ✅ **New feature — dirt paths that spawn only in the forest.** New node `Paths` (script `pathways.gd`) under `Main`, chunk-generated exactly like the trees (deterministic per chunk, loads/unloads around the player). Art in `harta/pathblocks/` (5 tiles, 64×64).
- ✅ **Forest-only, never desert or the blend.** Every tile of a candidate path is checked against `BiomeMap.desertness_at_chunk()`; the path is drawn only if **all** tiles are pure grass (`== 0`), so it never touches the desert **or** the soft gradient where desert meets forest. Verified at a biome boundary — paths stop with a clean buffer before the sand.
- ✅ **Shape.** 3 tiles across (a solid dirt strip). Runs **vertical or horizontal** (random). Length **random 4–20 tiles**. Roughly **1 path per 10 chunks** (`spawn_chance = 0.1`). Tiles are 64px = one grass cell, on the world grid; rendered at `z = -5` (above grass, below tree shadows/trunks).
- ✅ **Blend is done in-engine from a single tile.** Uses **only `pathblock normal`** everywhere; a small shader (`path_blend.gdshader`) fades each tile's alpha to transparent on the sides that face grass — decided per-tile from whether a path-tile neighbour exists. So the whole path softly melts into the grass on **all four sides and the two ends** (no hard cut, no protruding caps), and corners come out **rounded** for free (`min` of the two edge falloffs). The four pre-made `pathblock x grassblock *` tiles are no longer used. Fade width is `edge_fade` (0..0.5 of a tile).
- ⚙️ **How the per-tile edge mask reaches the shader.** Each distinct edge combination (there are ~9: 4 sides, 4 corners, interior) has its own **shared** `ShaderMaterial` with a `fade` uniform (`_mat_for(mask)`), and each tile picks the material matching its exposed edges. *Not* `set_instance_shader_parameter` (hits Godot's "too many instances using shader instance variables" cap), and *not* `self_modulate` — measured that Godot only reliably delivers the **R and A** channels of a 2D sprite's vertex colour to the shader, so packing the mask in RGBA silently dropped the **top and right** fades (only south/west blended). Shared-material-per-mask sidesteps both and still batches.
- ✅ **No black speckles on the edges.** `pathblock normal` has near-black pixels scattered in its dirt texture; faded to partial alpha over grass they showed as black dots on the margins. `_clean_texture()` lifts every pixel below `dark_floor` brightness once at startup (scaling to keep its hue; pure black → a dark-dirt brown), so the faded edge is dark dirt melting into grass, never black. The interior only loses its very blackest specks (subtle).
- ✅ **No trees on a path (or its blend).** Trees and paths are generated independently, so a tree used to grow straight through a path. `pathways.gd` now exposes `is_on_path(world_pos, margin)` (recomputes the deterministic path tiles around a point — no dependence on load order); `props.gd` skips any tree whose base lands within `path_clearance` (2 tiles) of a path tile, keeping trunks *and* overhanging crowns off the path and its faded border.
- ✅ **Paths never overlap into side bulges.** Two independent paths could partially overlap and leave a lump sticking out the side. Each path now computes its raw tiles (`_raw_path`, cached) and **yields** (isn't drawn) if it comes within `path_gap` (3 tiles) of a path from a lower-keyed neighbour chunk — deterministic tie-break, same idea as the trees' spacing. Result: every path is a clean straight strip, vertical or horizontal. Knobs on the `Paths` node: `spawn_chance`, `min_len`/`max_len`, `tile_px`, `edge_fade`, `dark_floor`, `path_gap`, `load_radius`; on `Props`: `path_clearance`.

## Current state (2026-07-21, performance pass)
*The game used to crawl ~2 minutes into Final Swarm — 144 FPS → 4 FPS. Measured, not guessed: an instrumented run that jumps straight to 10:00 and logs FPS + a per-script node census every 5s.*
- 🐞 **XP gems were never removed** — the whole cause of the late-game slowdown. In Final Swarm ~30 enemies die per second and you cannot possibly collect them all, so the gems piled up forever: **5390 gems / 17k nodes at 13:00**, each an `Area2D` animating itself every physics frame. Nodes are now flat at ~1500 and the run holds **144 FPS**, via bubbles:
- ✅ **XP bubbles (`xp3.tscn`).** When **`CLUSTER_NR` = 20** gems of the same kind end up within **`CLUSTER_RAZA` = 260px** of each other, they all **fly into their centre and merge into one bubble** worth exactly their total. Nothing is deleted behind your back and no XP is lost — you *see* it happen. Bubbles merge with each other by the same rule, so however long the run goes, the gem count stays low on its own (measured: ~80 gems + ~70 bubbles, steady, with single bubbles worth 26 000 XP). The **rare xp2 gem never merges** (Răzvan's call — it should stay recognisable). ⚠️ The check runs on the **newly dropped** gem via `call_deferred`, **not** in `_ready`: whoever spawns a gem sets its position *after* `add_child`, so in `_ready` it is still at (0,0) and finds no neighbours — that bug made merging silently never happen.
- ✅ **The bubble is xp2's art, repainted red at runtime** (`_textura_rosie` in `xp.gd`): every pixel gets hue `NUANTA_BULA` (0.0 = red) and keeps its own saturation and value, so the spiral keeps its shading — same drawing, different colour, processed once per run and cached in a `static`. There is deliberately **no `xp3.png` file**: swap `xp/xp2.png` and the bubble follows automatically, with no reimport. A red *overlay* was tried first (additive and mixed) and rejected — the orb stayed blue, or went muddy. See `debugging/geme_xp1_xp2_xp3.png` for how the three read on grass.
- 🐞 **Thunder God spawned one arc per enemy in range, per impact.** In a crowd that is quadratic: **4400 live arcs**, each an `AnimatedSprite2D` with a per-frame `_process`, dragging 300 enemies down to **6 FPS**. Two caps in `player.gd`, both **visual only — every enemy in range still takes the damage**: `THUNDER_MAX_ARCE = 10` arcs drawn per discharge, and `THUNDER_MAX_ARCE_VII = 60` arcs alive on screen in total. Past ~10 overlapping arcs you can't read them anyway.
- ✅ **Enemy hit-flashes are a float countdown, not a Tween** (`enemy.gd`). One `Tween` object per hit is clean until an aura + Thunder God hit 300 enemies several times a second — thousands of allocations per second for a 0.12s colour fade. `_flash_time`/`_flash_dur`/`_flash_color` are drained in `_physics_process` and lerp to the current tint; behaviour is identical (and now the tint tracks the freeze colour *live*). Also: enemies **cache the player node** instead of doing a group lookup every frame (×300), and only call `anim.play()` when the direction actually changed — the same rule `player.gd` already followed.
- ✅ **`Fx` has budgets** (`fx.gd`): at most **45** damage numbers, **25** spark bursts and **35** glow flashes alive at once; requests past the cap are skipped. An aura pulse catching 200 enemies asked for 200 `Label`s in one frame. ⚠️ The counters are reset in `_world()` whenever the current scene changes — the tweens that decrement them belong to nodes in the old scene and die with it, so without the reset the budgets would stay stuck full and **all effects would vanish after a few restarts**.
- ✅ **`Audio.play()` rate-limits per sound name** (`MIN_GAP_MS = 45`). The hit/death sounds are currently missing from `SFX` so nothing changes today, but when they are added back, Final Swarm would ask for them hundreds of times a second — a wall of noise and a pointless cost.
- ℹ️ **Measured result** (worst case: 300 enemies, the spawner's cap, plus Thunder God): **6 FPS → 90-144 FPS**. With a fast-killing build, a full run stays pinned at the refresh rate. The 300-enemy cap itself (`spawner.max_enemies`) is **not** the problem — 300 bodies with no Thunder God ran at 118-144 FPS even before this pass.

- ⚠️ **The background is a frame sequence, not a video — on purpose.** Godot only decodes **Ogg Theora** (`.mp4`/H.264 is not in the engine), and every Theora conversion we produced came out **corrupted** (confirmed independently: the source mp4 decodes clean, the `.ogv` fails in ffmpeg's *own* decoder with `unpack_block_qpis`, 92% error rate). So `menu/main menu background.mp4` is sliced into **60 WebP frames** in `menu/bg_frames/` (640×360, 10 fps, 6 s) played **ping-pong** (forward then backward) so the loop has no visible seam. **Do not "upgrade" this back to a VideoStreamPlayer** without re-testing decode.
- ℹ️ **Why the frames are full-res** *(2026-07-26)*: they are **1920×1080**, the source's own resolution. They used to be **640×360**, on the theory that the blur hides everything — but the animation starts on frame 1 while the picture is still **sharp**, so the opening second was a 3× upscale, and it showed. The reason 720p was rejected back then still stands for *lossless* import: 60 frames × 1920×1080×4 B would be **~486 MB of VRAM** (measured, not estimated). The fix is the import mode — the frames are now **VRAM Compressed** (`compress/mode=2`) instead of lossless, so the whole set costs **~62 MB** and total texture memory went **62.5 MB → 77.5 MB** for **9× the pixels**. Block compression is normally a poor fit for flat-shaded art, and PSNR against the source actually *drops* (32.3 → 30.2 dB) — but PSNR rewards blur, and a side-by-side crop shows the opposite of what that number suggests: tree edges and cloud outlines are crisp where they used to be mush. **If you regenerate the frames, keep `compress/mode=2`** or the menu will try to allocate half a gigabyte. On disk: **5.1 MB**.

### Y-sorting rule (read before adding any world object)
The player's sprite is **centred** on its sort point, so it extends ~64px **below** it. An object whose art ends exactly at its own sort line can never fully cover the player — the legs stay sticking out underneath. Trees solve this with `sort_anchor` (art hangs 73.8px below the sort line) and the statue with `ACOPERIRE_JOS = 74`. **Any new object that should occlude the player needs its art to hang more than ~64px below its sort line.** If you move that art, move its `CollisionShape2D` by the same amount or the hitbox detaches from the sprite.
